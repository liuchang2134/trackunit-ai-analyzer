# 机联智检 · 参赛说明

辅助已有车联网平台的工程机械 AI 排查工具。交付：网页工作台 + Chrome 侧栏插件。模型走云端 **DeepSeek**（关闭思考模式），设备资料、草稿与检查记录全部留在本机。

## 一、问题

设备出故障时，现场工程师手上是这么几样东西：车联网平台上一条故障码、一份几百页的官方手册、一个零件图册。他要在三者之间来回翻，凭经验猜哪个部件可疑，再去图册里找对应料号。

把通用大模型接进来解决不了这件事——**它看不到设备数据，也不知道该翻手册哪一页**。直接问它"E4030 是什么故障"，得到的是听起来合理但无法核实的一段话。

我们的判断：AI 在这类场景里的价值不在于"会聊天"，而在于**能不能把设备证据、手册依据、真实料号串成一条可核查的链**。

## 二、AI 做了什么

三步，每一步都能在界面上看到 AI 的具体动作：

**1. 读什么，由它决定。** 程序按证据规则读取设备数据并做数值计算，模型负责**选择下一步读什么、何时停止**。最后一次真实运行中它自己决定追加读取备件目录（另外 3 项读取是任务规定的，不计入它的选择）。

**2. 揣测哪里坏，并给出手册页码。** 对 E4030，模型给出 4 个可疑部件，每个都带手册页码、检索词和推理说明：

| 可疑部件 | 手册依据 | 检索词 |
|---|---|---|
| ECU 供电熔断器 | 第 286 页 | ECU fuse、fuse blow |
| ECU CAN 线束 | 第 286、287 页 | CANH2、CANL2、lead wire break |
| 线束连接器 | 第 287 页 | connector、pin rusted |
| ECU 与控制器 | 第 287 页 | ECU failure、controller fault |

**3. 在官方图册上把目标标出来。** 打开对应 VIN 的官方图册后，插件把上表的检索词**直接标在页面上**（青色标记），工程师不必盲翻；读回真实条目后由模型给出料号候选。

**AI 的贡献与程序的贡献分开计量**，不把程序读到的数据算成模型的功劳。

## 三、怎么相信它

AI 诊断最怕"看起来合理但引用是编的"。我们把它做成可检查的：

| 检查什么 | 怎么做 | 当前实测 |
|---|---|---|
| 引用是否指向真实证据 | 把每条引用逐条对回报告实际记录的证据集合 | **63 条引用，0 条悬空** |
| 结论是否都带检查方向 | 统计未给检查方向的部件假设 | **12 个假设，0 个空口** |
| 说的和做的是否一致 | 演示页只放真实模型输出，预设脚本已彻底移除 | **4 条真实 AI 运行可回放** |
| 数字能不能自己重算 | 一条命令重新生成评估报告 | 见下 |

## 四、你可以自己复核

全部离线，不调用模型、不产生费用：

```bat
:: 重新计算上面所有 AI 依据数字（含所用代码的哈希）
.tmp\venv\Scripts\python.exe scripts\evaluate_ai_grounding.py

:: 跑全量回归
.tmp\venv\Scripts\python.exe -m pytest tests -q
node --test tests/*.test.cjs
```

网页端打开 <http://127.0.0.1:8890/assistant-ui/> → 「演示案例」，可看真实模型输出并**下载 AI 排查证据包**（Markdown，含每个可疑部件的手册页码、检索词、引用来源与推理说明）。

### AI 在真实浏览器里被验证过

不只是单元测试。三个探针各自启动一个真实 Chrome，跑真实产品代码（逐步演示见 [演示路径.md](演示路径.md)）：

```bat
:: 侧栏在真实 Chrome 中渲染：设备识别 + 与工作区握手（8 项检查）
node scripts\extension_probe.mjs

:: AI 检索词标注在图册正确的行上：本地以真域名 https://xgss.xcmg.com 提供夹具（9 项检查）
node scripts\xgss_marking_probe.mjs

:: 侧栏 AI 建议面板：连通、状态落定、无建议时给明确指引（6 项检查）
node scripts\sidebar_guidance_probe.mjs --report .tmp\g.json
```

图册标注那一项值得单独说：用 E4030 真实运行产出的 12 个检索词作输入，8 行表格中**恰好 5 行被标注、3 行未被标注**——后 3 行是故意放的反例，如果匹配逻辑退化成一标全标，检查会失败。

## 五、诚实边界

把没做到的写清楚，比多讲两句成绩重要：

- **我们度量的是"引用能否对上证据"，不是诊断正确率。** 正确率需要带标签的验证集，本机没有，因此**不作任何准确率声明**。
- **样本量很小**：20 条记录中只有 4 条真的调用过模型，且多为同一台设备的测试输入。这些数字不能外推。
- **故障码是测试输入**（E4030 为独立测试场景），不代表设备实际发生过该故障。
- **可疑部件是待核查方向**，不是已确认故障；部件出现在图册里也不代表它已损坏。
- 耗时数字取自历史记录，受当时网络与模型负载影响，**不是性能基准**。
- **三件事必须在真实 Chrome 里人工完成，自动化无法替代**：
  1. 把侧栏**作为浏览器侧边栏**打开（需要用户手势；且当前 Chrome 已不支持用 `--load-extension` 加载未打包扩展，只能手动加载）；
  2. 在**已登录的真实 XGSS 页面**上确认标注（夹具的结构可能与真实站点不同）；
  3. 窄屏"取回地址 → 新标签页打开图册"整链路。
- **侧栏把 AI 检索词渲染成列表这一环尚未端到端验证**：工作区只回应来自 `chrome-extension://` 的检索词请求（这是刻意设计，网页不该响应任意来源），而自动化无法伪造该来源，因此只能在真机确认。

## 六、开发过程中的一个真实修复

这套验证不是走过场。第 15 轮做端到端联动时查出一个缺陷：

**从「诊断记录」打开一份含 AI 分析的报告后，侧栏拿不到任何检索词**——它会说"尚无 AI 建议。请先完成一次 AI 分析"，**而报告就在屏幕上**。用户因此无法在图册上标注 AI 目标，而这正是本项目的核心动作。

根因是两个文件之间的接缝：报告变量只在**新分析完成时**赋值，历史重开走的是另一条渲染路径，**从不发布它正在显示的那份报告**。修复用了独立变量而非覆盖——覆盖会把流程条、导出与反馈面板悄悄切到历史快照上。

| | 修复前 | 修复后 |
|---|---|---|
| 检索词 | 0 | **12** |
| 部件假设 | 0 | **4** |
| 故障码 | null | **E4030** |

这类"看起来接通、实际断掉"的问题，单看任何一个文件都发现不了，只有让整条链路跑起来才会暴露。

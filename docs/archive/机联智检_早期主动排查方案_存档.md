# 机联智检项目计划书

## 工程机械车联网异常主动排查与验证平台

AI＋工程机械创新创业竞赛｜完整参赛 Proposal

版本日期：2026年9月14日（北京时间）

项目阶段：软件底座和机制仿真数据已具备，主动排查及对照评测拟开发。

资源约束：个人主导，使用现有电脑与已购AI会员，零新增现金开发预算。

本计划书面向竞赛评审及潜在试点合作方，说明项目要解决的业务问题、产品与技术方案、已有成果、验证方法、商业路径和实施安排。建议以柴油液压挖掘机的数据链路异常为首期边界，完成可复现的主动排查原型，并通过独立对照实验决定是否进入实测试点。

### 执行摘要

工程机械车联网中的“离线”并不总意味着设备停机。传感器不再刷新、车载终端失去供电、通信中断、云端入库延迟和本地缓存过期，都可能形成相近的界面表现。技术支持需要核对多个系统和现场信息，才能选择有效的下一步检查。

机联智检拟将这一排查过程产品化：读取当时可获得的遥测与时间证据，维护候选原因，按区分能力与执行成本选择下一项检查，收到结果后更新判断，输出带证据的交接报告。信息不足时，系统明确保留未决结论。

项目基于已有 Trackunit AI Analyzer 软件底座开发，现已完成42个虚拟设备班次、336小时的柴油液压挖掘机机制仿真数据。物理工况、传感器、网络、云端及缓存分层生成；全部班次通过内置一致性检查，13项专项自动测试通过。这些成果证明生成与检查流程可运行，尚未证明现场诊断准确率或维修收益。

首期交付是一套“主动排查助手＋独立场景评测环境”。前者服务于异常处理，后者提供开发、复现和培训条件。商业切口优先选择车联网研发及技术支持团队的固定范围流程评估，实测验证后再拓展海外经销商远程支持。

**核心目标：在同等证据、检查权限和计算预算下，保持结论质量，减少无效检查。**

正式申报时需补入参赛主体、实际团队成员及相应证明材料。本稿不代填未经确认的身份、客户、合作关系、知识产权或经营业绩。

## 一 业务问题与应用边界

### 典型任务

某台挖掘机的运行小时和油量已经一段时间没有变化。支持人员首先需要判断，设备确实未运行，还是数据没有传到当前页面。平台显示的值可能来自较早采样，因此“读取成功”和“信息新鲜”需要分别检查。

如果过早认定终端故障，可能增加现场检查负担；如果把真实异常当作正常停机，又可能延迟后续处理。项目研究的是减少这种信息不充分下的排查迂回，具体频率和成本需要试点测量。

### 用户与任务分工

|角色|需要完成的任务|平台提供的支持|
|---|---|---|
|车联网研发与测试人员|复现异常并检查系统行为|可控场景、时间线、数据层审计及回归评测|
|远程技术支持人员|判断下一步要查什么|候选原因、证据缺口和检查顺序|
|现场服务人员|完成明确且有依据的观察|结构化检查请求和结果记录|
|技术支持负责人|复盘流程质量和工作量|逐步证据、检查成本及结论报告|

首期买方假设是具有车联网技术支持职责的组织，日常用户是研发测试及技术支持人员。决策权和预算来源必须通过访谈确认，不能仅凭使用需求推断付费意愿。

### 首期范围

限定为柴油液压挖掘机的挖装工况，以及正常运行、正常停机、通信中断、终端断电、油量信号冻结、缓存过期和云端批量延迟七类情形。正常类是必要对照，不能让系统遇到任何输入都输出故障。

当前云端批量延迟是单设备记录积压后集中到达的模拟，并非已经实现多设备区域故障诊断。后续若加入同区域设备对照，需要生成共享网络与云服务状态，不能把独立随机班次直接拼成真实车队。

本轮不包含液压泵、发动机内部故障确诊、剩余寿命预测、零件推荐或远程控制。涉及现场操作的动作，在实测试点前应按具体机型和服务规程核实；仿真检查接口不构成现场作业指导。

## 二 产品设计与使用流程

### 一次排查如何完成

用户选择异常设备后，平台先展示最近数据及其采样时间，再给出若干候选解释。系统为每个解释列出已知证据、冲突证据和待确认条件。用户执行推荐检查，系统接收结果并更新候选集合，直至形成可支持的结论、达到检查预算或证据无法继续获取。

报告将“观测事实”“模型推断”和“待核实事项”分开。例如，云端样本时间比本地缓存更新是事实；本地缓存更新环节异常是有依据的推断；具体软件故障位置仍需日志确认。系统不把排查层级定位自动升级为部件损坏结论。

### 核心页面

|页面|用户可以看到或操作的内容|当前状态|
|---|---|---|
|设备总览|设备状态、累计小时、油量、更新时间|已有原型，需接入新数据|
|异常工作台|候选原因、证据、已完成动作及下一步检查|拟新增|
|场景实验室|选择场景、隐藏原因、设定证据可用性|生成器已具备，界面拟新增|
|诊断回放|逐步展示决策、结果和实际原因|已有输入数据，拟新增|
|评测中心|逐案例结果、分组指标、方法对照|拟新增|
|报告中心|导出设备与排查记录|已有导出代码，需扩展内容|

### 示例交互

用户提问：“这台设备是不是停机了？”系统发现本地记录已经陈旧，将正常停机、传输异常和缓存异常列为待检查解释。它首先申请读取云端最新样本时间。如果云端数据新鲜而本地仍旧，优先调查缓存；如果云端也旧，再判断终端供电和通信情况。现场无法提供证据时，保留多个解释。

这是拟实现的交互示例，并非已发生的客户案例。演示中所有动作结果由固定时刻的模拟环境返回，避免使用演示结束后才出现的信息。

### 交付形式

参赛版提供本地 Web 应用、可复现数据和生成器、方法对照记录、演示视频及项目说明。前端、FastAPI后端、SQLite和Ollama模型服务全部部署本机。真实本地模型推理是交付必选项：用户自由提问，模型提出检查调用，读取结果后更新结论。模型及依赖首次下载需联网；模拟数据演示完成安装后应能断网运行。

## 三 本地部署架构与数据接口

### 分层架构

本地浏览器连接FastAPI，后端调用本机Ollama并读取SQLite及数据文件；不调用云模型。系统按“数据输入→证据整理→主动排查→过程记录→独立评分”组织。数据输入可来自模拟平台观测或经授权的 Trackunit 接口。证据整理层统一时间、单位、缺失值与来源，主动排查层只读取规定范围内的信息。独立评分器持有隐藏原因和完整轨迹，运行权限与诊断模块分开。

|组件|职责|技术与接口安排|
|---|---|---|
|接入与缓存|读取数据并保留采样时间|复用 Trackunit 客户端和 SQLite；现场适配待验证|
|场景服务|载入当前案例和决策截点|新增场景读取接口，服务端裁切历史|
|证据存储|保留值、单位、来源、时间和可用性|结构化记录及原始引用|
|排查引擎|维护候选原因并选择动作|规则约束、启发式策略及可选模型规划|
|动作执行服务|检查权限和预算，返回单项结果|只读查询或人工观察结果；仿真阶段使用结果接口|
|评分与回放|比较结论与真值，复盘过程|独立运行，禁止将真值返回规划上下文|

### 拟新增接口

GET /diagnostic/scenarios 返回可用场景元信息，不返回标签。POST /diagnostic/sessions 创建排查会话。POST /diagnostic/sessions/{id}/checks 接收检查名称，核验权限、可用性和预算后返回结果。POST /diagnostic/sessions/{id}/conclusion 保存结论或未决状态。GET /evaluation/runs/{id} 返回评分结果，仅评测角色可见。

上述路径是设计接口，当前尚未实现。客户端不得自行上传“正确答案”作为检查结果；现场人工输入应单独记录人员、时间、来源和可信度。

### 时间与权限

证据至少保留事件时间、平台可见时间和本次读取时间。现场 API 未提供独立入库时间时，标记未知，不能以读取时间补造。当前合成数据记录了样本时间，部分入库信息仅在评测层保存。

模拟输入已在文件层裁切，但目录隔离不是访问控制。参赛版还需增加服务端权限校验、独立评测配置和逐次调用审计。真实凭据仅由后端管理，评测标签、完整未来回放及密钥不得进入前端诊断上下文。首期保留单组织本地部署，暂不宣称支持多租户生产服务。

## 四 主动排查方法与创新验证

### 从证据到检查

初版将每种原因表达为可核验的条件集合。例如，缓存异常需要比较云端与缓存时间；终端供电和网络连通应使用相应检查证据。维护三种证据状态：支持、冲突、未知。没有收到数据本身通常不足以证明设备停止。

候选集合需要保留“当前原因库之外”的未解释状态。现有数据集尚无独立未知原因类别，在正式评测前应补入；否则容易把七类闭集分类误认为通用诊断。

对每项检查，估计它在当前候选集合中能区分多少解释，再结合成本、可用性和已有检查记录进行排序。初版可用候选集合划分的均衡程度作为信息价值代理。该分值只是选择检查的启发式，不包装为经校准的真实故障概率。

### AI的具体作用

开发阶段使用已购AI会员辅助代码、测试和材料编写。应用运行时，由本地大模型理解中英文问题、形成候选解释、选择检查工具并解释结果；模型参与实际决策，不只润色固定结论。确定性程序负责动作白名单、预算、证据引用和停止规则。通过Ollama工具调用或结构化JSON传递动作请求。[S6] 模型输出必须通过结构校验；失败时记录错误，不能生成假检查结果继续流程。

停止条件包括：获得足以支持当前层级判断的证据；剩余动作不可执行；达到预算；或检查未带来有效区分。此时输出确定结论、候选集合或未决状态，并解释原因。

### 拟验证的贡献

|研究问题|拟实现的方法|证据要求|
|---|---|---|
|能否减少无效检查|结合候选区分能力和成本选动作|同一测试案例的成本及质量对照|
|能否减少跨层误判|显式比较设备与链路的时间证据|逐类混淆和错误确定结论记录|
|能否约束大模型臆断|结构化证据引用与结果校验|引用正确率、无依据结论及失败日志|

这里的贡献是待检验的工程方法，不声称提出全新信息论或通用诊断算法。若规则策略已经足以解决问题，应保留简单方法；若大模型只改善语言交互，应如实报告其价值所在。是否需要概率模型或强化学习，在获得足够有代表性的数据后再决定，当前不增加训练复杂度。规则引擎作为校验层和实验对照，不能替代必需的本地AI闭环。模型不可用时明确停止AI会话并提示修复，不切换成伪装为AI的预制答案。

## 五 工程工况与数据可信度

### 已完成的数据

42个虚拟设备各运行一个8小时班次，总计336设备小时。内部状态按5秒步长生成，共241,920条；全班次平台查询按1分钟记录，共20,160条。训练、验证、测试分别为28、7、7班，设备身份互不交叉。七类情形各6班，均衡设计用于方法比较，不代表现实频率。[S5]

挖掘循环包含暖机、挖掘、重载回转、卸料、空载回转、等车怠速、短途行走、午休及收工停机。参考XE135U北美手册的90 kW功率、500 N·m最大扭矩、250 L油箱和速度边界约束通用模拟模型。手册存在2100与2200 rpm额定转速文本冲突，生成器采用保守上限并记录该差异。[S1]

### 真实依据与假设分开

|内容|依据或性质|可以支持的结论|
|---|---|---|
|功率与容量边界|公开产品手册|检查数值不越过参考包络|
|燃油和小时积分|生成器确定性计算|检查时间与消耗自洽|
|动作顺序与时长|半马尔可夫状态模型及假设分布|构建连续工况，不代表实测周期分布|
|油耗与温度曲线|显式经验结构和未校准系数|用于仿真敏感性，不用于现场性能预测|
|延迟及证据缺失|模拟配置|验证方法在这些条件下的表现|

现有专项检查包括燃油平衡、计时、轴功率及扭矩边界、等效液压功率、温度连续性、位移与行走速度关系，以及断网不改变物理作业轨迹。13项测试通过与全部班次一致性通过，均属于软件和机制检查结果。[S5]

### 当前局限与改进

同源模拟器容易形成方法偏好。当前故障注入时间范围较窄、均为单一异常、动作结果较理想化，油量独立采样时间也未必是现场 API 可用字段。正式对照应随机化事件时刻，加入动作误差、未知原因、延迟恢复和终端休眠情形；同时移除不具备现场可得性的字段进行消融。

云端延迟检查当前结果过于直接，需替换为可观察的入库计数、时间差等原始证据，避免把模拟标签变成答案接口。真实数据校准前，项目将成果表述为工程约束机制仿真，不宣称完成真机数字孪生或现场诊断验证。

## 六 对照实验与技术指标

### 实验设计

正式比较采用相同初始证据、动作权限、成本表和停止预算。固定顺序、随机选检查、本地模型直接选检查、受证据与成本约束的本地模型选检查组成必做对照，均在本机运行。固定模型版本与上下文预算，单独报告模型时延。模型推理及对照尚未运行，不预填成绩。

每个基础工况产生的不同异常变体留在同一数据分组。建议先扩展100个独立基础工况，每个生成七类变体，共700个场景；以60、20、20个基础工况分为训练、验证和测试。这是拟执行的评测规模，当前仅有42班初始数据。

模型版本、提示词、参数、调用预算和成本定义在测试前冻结。测试集不得用于调整规则或挑选演示胜例；以基础工况为统计单位，报告配对成本差及区间估计。增加参数越界测试集评估温度、动作时长和丢包假设改变后的表现，同源分布外测试仍不能替代真机验证。

### 指标口径

|指标|定义|
|---|---|
|总体正确率|正确且确定的结论数除以全部案例数|
|结论覆盖率|给出确定结论的案例数除以全部案例数|
|已决准确率|正确结论数除以已给出确定结论数|
|错误确定结论率|错误且确定的结论数除以全部案例数|
|检查成本|全过程动作成本之和，报告均值及分位数|
|人工介入|标为人工的动作次数，另计不可用请求|
|时延与调用|端到端时间、模型调用次数和实际用量|

所有指标需按类别和证据可用程度分组；拒答、超预算、接口失败均保留。除真实原因评分外，评测器还需判断现有可得证据是否允许唯一结论；对不可辨识案例，评价候选集合和克制性。

### 内部验收目标

交付底线是完成所有案例回放、无未来数据或标签泄漏，并输出完整逐案例日志。拟设性能目标：相对固定清单，平均模拟检查成本降低至少15%，总体正确率下降不超过2个百分点，且错误确定结论率不升高。以上是研究目标，不是已取得的结果；同时检查区间估计，若证据不足或未达标，则报告失败并调整方法。

## 七 竞争格局与项目差异

### 已有能力应被承认

Trackunit IrisX MCP已支持自然语言访问车队信息，并提供相关业务动作能力；其维护方案包含故障、服务和设备健康功能。[S2][S3] 徐工公开的CONNECT体系包含ONE、Maia和HANYUN OS，覆盖设备监测、AI辅助诊断、工单及服务协同。[S4] 这些公开功能说明，通用看板、聊天、告警和报告本身不足以成为项目的主要差异。

|现有方案|已确认覆盖|本项目拟验证的切口|
|---|---|---|
|Trackunit车队平台及AI接口|自然语言查询、车队及维护信息|在可用检查和成本约束下逐步补证|
|徐工CONNECT及Maia|设备监测、诊断与服务协同|数据链路层定位与独立场景验证|
|传统固定检查清单|确定、可审计的排查顺序|随证据变化调整顺序和停止条件|
|通用大模型问答|语言理解与解释|检查权限、时间证据和结论约束|

右列是拟开发和验证的功能，不是“竞争方没有”的断言。目前未完成覆盖全部现有及在研产品的能力核查，也未取得正式专利查新结论。

### 竞争核验方法

试点前应以相同场景询问现有系统：能否区分云端与本地缓存问题；能否根据刚获得的证据重新选择检查；能否显式处理证据不可用；是否保留可复现的检查成本和评分。核验输入、输出、操作流程和证据，而不是只比较功能名称。

如果现有平台已经提供等价流程，项目需要转向专门的集成验证或场景评测价值；如果仅添加少量脚本就能解决全部需求，应降低独立产品预期。若主动策略没有超越相同动作权限的简单方法，也不以大模型包装替代实验结果。

### 可持续积累

长期资产应来自经授权的真实链路事件、经服务人员复核的检查动作、可重放的评测集及稳定接口适配。现阶段尚未形成这些壁垒。项目的近端优势是已有可运行软件基础和机制模拟器，能够较低成本地提出、检验和淘汰排查策略，并在现有电脑与会员范围内推进。

## 八 商业模式与客户验证

### 首个可交付产品

首期不依赖大规模设备订阅，而以一个明确边界的技术评估项目进入：选定一种数据链路、整理若干已确认事件、构建回放、比较现有排查流程，交付证据报告及原型。买方可先验证结果是否有用，再决定部署范围。

目标组织包括工程机械厂商的车联网及海外支持团队、终端集成服务商、具有独立技术支持能力的经销商。这里是目标客户画像，不代表已经接触、合作或获得采购意向。

### 访谈与试点步骤

在不增加现金支出的条件下，争取通过现有联系渠道访谈5至8名潜在使用者，记录最近一次异常的实际处理过程：用了哪些系统、检查由谁执行、多少次沟通、最终如何确认，以及哪些信息无法取得。如有单位自愿提供授权数据和人员配合，再开展4至6周小范围试点；当前未落实合作，不安排付费数据采购或差旅。

试点建议收集不少于30个已确认事件，按正常、终端、网络、平台等实际覆盖情况记录；该样本只适合初步探索，不支持普遍效果结论。盲测时先隐藏最终原因和后来信息，再让不同方法处理同一事件，最后由技术支持人员复核判断与建议。

### 收费与经济性假设

|形式|交付边界|当前状态|
|---|---|---|
|固定范围评估服务|约定事件、数据接口、对照及结果复盘|优先验证的商业切口|
|内部软件许可与维护|已验证流程的部署、更新和支持|需要试点后的报价验证|
|场景与接口定制|特定机型或链路回放与适配|按需求及工作量评估|

商业化作为参赛后的可选路径：只有获得明确需求后再商定报价和交付范围。当前没有收入承诺，也不以先行垫付资金、购买数据或租用服务作为项目完成条件。

试点价值核算采用客户确认的数据：实际节省的支持时间乘以约定小时成本，加上有记录且可归因的其他支出变化，再扣除模型、部署和维护成本。避免重复计算工时与出差收益；没有证据时不将“避免停机”计入收益。正式报价应覆盖交付人工和支持成本，不能仅与API费用比较。

本稿不提供未经来源支撑的行业市场规模，也不把全球设备保有量直接乘以假定订阅费。先验证一个买方、一项任务和可付费结果，再估算可服务市场。

## 十 个人开发安排与风险管理

### 个人主导与AI辅助
